## 运行入口与阅读约定

当前运维方式见 [迁移与真机运维手册](MIGRATION-AutoJs6.md)：通过 `tools/build.js` 从 `tools/build.py` 提取引导、日志、运行器片段，拼入 `src` 模块，生成 `build/bundle.js`，部署为手机上的 `_main.js`。电脑服务的 `/src/main.js` 在构建产物存在时返回 bundle。

因此，修复任务模块应修改 `src`；修复心跳、投递、启动、日志应检查 `tools/build.py`。不要只改生成后的 bundle。源码修改完成后，按项目惯例重建、语法检查和部署，再回归。下面的行号均指审查基线，修改后可能偏移。

## R01：快捷圆盘的回调绑定错误

**位置**：[src/ui.js](../src/ui.js)，238、265–270 行，`_dockRow()`。

循环使用 `var t = items[i]`，监听器回调直接读取 `t.id` 和 `t.title`。同一次函数调用内所有回调共享该变量，点击时取到的是该行最后一项。

- 第一行最后一项是小乔，所以信息、邮件、小乔三个按钮都会启动小乔。小乔会花元宝，这使普通信息按钮也具有意外消费后果。
- 第二行最后一项是 `null`（更多），所以日常、截图按钮会在读取 `t.id` 时出错。
- 完整面板通过 `_row(t)` 的独立参数绑定任务，不存在同一个循环闭包问题。

**建议**：提取独立按钮创建函数，或使用适配 Rhino 的立即执行函数保存任务对象。不要直接假定目标 AutoJs6 对所有现代 JavaScript 语法均兼容。

**验收**：用替代的 `runTask` 收集参数，逐个触发圆盘六个按钮，核对任务 ID；更多只展开面板。验证不得真的运行小乔消费。

## R02：任务互斥和停止机制不可靠

**位置**：[src/ui.js](../src/ui.js)，470–472、475–512、516–563、566–572 行；[src/tasks/xiaoqiao.js](../src/tasks/xiaoqiao.js)，35、170–176 行；[tools/build.py](../tools/build.py)，259–262 行。

存在四个关联问题：

1. `isBusy()` 只按 `_t0` 判断，超过 300000ms 就空闲，没有检查线程是否完成。小乔允许等待 420000ms，确认再次执行还会重置截止时间，因此合法运行中的旧任务可能被视为空闲。
2. 远程 `run:` 指令先把 `_t0` 清零，直接绕过已有任务的忙碌检查。
3. `stopAll()` 调用 `interrupt()` 后立刻清空线程引用和忙碌状态，没有确认线程已经退出。中断可能延迟，或在捕获异常的路径中没有立即结束；具体行为需在目标 AutoJs6 上验证。
4. 旧任务 `finally` 无条件清空 `_thread` 和 `_t0`。如果新任务已经启动，旧任务收尾可能覆盖新任务状态。收尾前还会先释放状态，再执行截图/日志请求，这段时间旧线程实际上仍在运行。

**建议**：统一所有启动入口，建立受保护的任务运行状态和任务 ID；只有当前任务可以清理自己的状态。取消时设置协作取消信号、请求中断，等实际退出后再释放互斥。把执行超时与忙碌状态分开，超时不能只修改状态。耗时网络回传也需要明确的生命周期和串行策略。

**验收**：模拟超过五分钟的任务，分别从圆盘、面板、投递和远程命令请求第二个任务；确认不会并行操作。验证停止后马上启动、旧任务稍后退出，不会清掉新任务状态。测试阶段可缩短时间或注入时钟，不必等待真实七分钟。

## R03：小乔识别失败仍点击消费按钮

**位置**：[src/tasks/xiaoqiao.js](../src/tasks/xiaoqiao.js)，37–41、65–89、149–153 行。

- `_openPanel()` 找不到头像时直接假定面板已打开，没有正向确认面板。
- `_openDailyTab()` 三轮均找不到开启按钮，仍返回固定坐标。
- `run()` 接收了 `btn` 却不使用它，无条件点击 `KAIQI_POINT`。
- `_findAvatar()` 支持左右两侧头像，但 `_openPanel()` 不管命中哪侧，都点击左侧 `(38,485)`。

识别失败、加载或其他弹窗出现时，流程仍会继续在未知页面点击。错误点击究竟落到什么功能取决于当时页面，不能凭静态代码断言一定购买了什么。

**建议**：先正向确认助手面板和日常页，匹配失败就报告失败并保留截图；使用实际命中坐标。消费操作前确认按钮、页面及必要的预算/重复执行约束，避免用固定点兜底掩盖未知状态。

**验收**：分别模拟头像消失、仅右侧头像存在、开启模板缺失、加载遮罩和其他弹窗；未知状态不得点击开启点，也不得宣告页面就绪。

## R04：返回主城兜底始终使用旧截图

**位置**：[src/tasks/xiaoqiao.js](../src/tasks/xiaoqiao.js)，137–142 行；[src/vision.js](../src/vision.js)，68–69、80–81 行。

`isHome()` 不传图片时调用 `frame()`，有缓存就直接返回。小乔最后的左上角返回循环只执行点击和睡眠，没有刷新截图，循环条件和最终检查均读旧帧。

**触发路径**：进入陌生子界面兜底时缓存为非主城 → 第一次点击已回主城 → 后两次仍按旧图判断、继续点 `(70,70)` → 最后仍按旧图抛错。若没有其他并发路径刷新缓存，这个分支无法看到点击后的变化。

**建议**：每次状态检查显式获取新帧，例如 `v.isHome(v.frame(true))`；同时明确识别 API 的帧有效期和点击后的缓存失效规则。

**验收**：模拟第一次返回即可到主城，后续不得重复点击，任务应正常结束。模拟始终无法返回，应有限次重试后失败。

## R05：投递指令被提前消费，忙碌标志无效

**位置**：[tools/build.py](../tools/build.py)，185–189、198–214、237–246 行；[src/ui.js](../src/ui.js)，481 行。

心跳设置 `__busy=true` 后，启动包装线程调用 `runTask()`；而 `runTask()` 又创建真实任务线程并立即返回，包装线程随即设置 `__busy=false`。

此时真实任务还在执行，下一条文件指令却会被读取并删除。若它是普通任务，`runTask()` 因忙碌拒绝执行，指令已经丢失；若是 `tap:`，还可能直接穿插点击。单个指令文件也不是多条任务队列。

**建议**：只有执行器确认接收后才消费任务；如需排队，使用明确的队列和完成/拒绝反馈。忙碌状态由真实任务生命周期驱动，手动点击也应遵循同一套互斥规则。

**验收**：A 运行时投递 B，B 应明确排队或明确拒绝并保留可追踪反馈，不能删除后静默丢失；普通任务运行时投递 `tap:` 不得无约束干扰。

## R06：异常后缺少恢复，主城可见不等于可操作

**位置**：[src/ui.js](../src/ui.js)，532–542 行；[src/tasks/xiaoqiao.js](../src/tasks/xiaoqiao.js)，182 行；[src/game.js](../src/game.js)，54–69 行；[src/vision.js](../src/vision.js)，72–76 行。

日常的邮件步骤失败后只记录和截图，紧接着执行小乔，未先恢复到已知页面。小乔超时也直接抛错，没有独立的清理/恢复流程。

主城识别为了兼容暗色遮罩，会放低阈值全屏找背景锚点，或读取底部征战文字；`ensure()` 又优先判断主城。因此弹窗覆盖下只要背景仍可识别，就可能提前视为主城就绪，跳过恢复。

**建议**：区分主城背景存在和主城可交互；失败后先有限次关闭已知弹窗、处理掉线，再决定是否继续后续任务。未知画面保留证据并退出，不盲点推进。

**验收**：在邮件未关闭、奖励弹窗和掉线弹窗情况下启动日常；小乔步骤应等待恢复或明确失败，不得在残留页面继续消费点击。

## R07：成功判据缺少业务结果确认

### 邮件

**位置**：[src/tasks/mail.js](../src/tasks/mail.js)，37–49、68–73 行。

找不到全部领取按钮就退出领取循环，后续关窗回主城仍报告成功。点击被 loading 吞掉也没有业务结果校验。代码注释明确接受该行为，但任务标题和成功结果没有表达“无法确认领取”。

**建议/验收**：区分已领取、无附件、无法确认和失败。按钮没找到或点击无响应时，不得宣称领取成功；应通过邮件状态变化、奖励结果或可识别的空状态验证。

### 小乔

**位置**：[src/tasks/xiaoqiao.js](../src/tasks/xiaoqiao.js)，44–58、159–168 行。

完成判定在较大区域内找到一个接近 `#80CF4C` 的像素即通过，颜色阈值为 60；任意匹配到的恭喜获得/贡献获得奖励浮层也直接触发收尾成功。这些信号未与整套日常完成建立足够关联。

**建议/验收**：结合正确页面、结果文本或结构化视觉特征、连续帧等信号，区分中间奖励和最终完成。用包含相似绿色、只有中途奖励的反例图验证，不能提前报完成。

### 玩家信息

**位置**：[src/tasks/playerinfo.js](../src/tasks/playerinfo.js)，58–64 行；[src/ui.js](../src/ui.js)，495–499 行。

字段解析为 `null` 只记错误，全部失败仍正常返回；外层忽略返回结果，照样显示完成。

**建议/验收**：任务返回明确的完整/部分/失败状态，由外层展示。模拟 OCR 全空和部分空，结果应能区分，不得统一显示成功。

## R08：等级后缀补全覆盖多数票

**位置**：[src/tasks/playerinfo.js](../src/tasks/playerinfo.js)，92–105、114–123 行。

后缀补全假设 OCR 只会漏前导位、不会多一位。但文件注释已记录 `920` 误识别，且解析允许其通过。候选 `[20,20,920]` 会先投票得到 20，再被更长且后缀相同的 920 覆盖。

**建议**：结合当前游戏真实等级范围、文本上下文和投票置信度处理，不无条件偏好更长数字；范围需核实，不能直接把三个样本账号的 120 当作游戏等级上限。

**验收**：覆盖 `[20,20,920]`、`[120,120,20]`、`[20,20,120]`、全空和全不一致场景；修复应有明确的取值/不确定策略，而非为了通过单个样例硬编码。

## R09：启动清理影响无关脚本

**位置**：[tools/build.py](../tools/build.py)，107–126 行。

遍历 `engines.all()`，只要不是自己就 `forceStop()`，没有判断是否属于本项目。用户同时运行的其他 AutoJs6 脚本会被停止。

**建议**：按可信的脚本来源路径或本项目标识，只清理本项目旧引擎；同时检查其他 clean/reload 分支对 AutoJs6 的引擎接口是否一致。

**验收**：同时运行本项目旧引擎和一个无关的测试引擎，启动本项目新版本后，只清理前者。

## R10：图片生命周期和无界日志

**位置**：[src/vision.js](../src/vision.js)，80–89、135–160、167、227–228、248–253、265–335 行；[src/tasks/playerinfo.js](../src/tasks/playerinfo.js)，35–40 行；[tools/build.py](../tools/build.py)，51–66 行。

取帧持续克隆图片，归一化、OCR、模板匹配还会创建裁剪图、缩放图和模板对象，当前没有明确的释放/复用所有权约定。不能仅凭没有 `recycle()` 就断言一定泄漏：AutoJs6 的自动回收时机和对象实现仍需核实。但长时间运行可能出现原生内存压力，应实际测量。

`LOGS` 持续追加而不裁剪，本地运行日志也持续追加而不轮转，是确定的无界增长。关闭 HTTP 只推进推送索引，并不会释放日志数组。

**建议**：先明确共享帧、任务持有多帧和临时图片的生命周期，再做模板缓存与受控释放；避免回收仍被玩家信息投票或其他线程引用的图片。日志使用有界缓冲和文件轮转。

**验收**：在目标设备连续运行并记录内存、图片相关异常、日志大小和任务成功率；对比修改前后趋势。必须覆盖玩家信息同时持有三帧的场景。

## R11：缩放降级只处理了部分坐标

**位置**：[src/vision.js](../src/vision.js)，145–147、174–181、265–270、337–349 行；[src/tasks/xiaoqiao.js](../src/tasks/xiaoqiao.js)，49–51 行。

resize/scale 失败时保留较小裁剪图并设置 `_scale`。部分 ROI 会映射，但模板未同步缩放，匹配点仍可能处于缩小图坐标；固定点击仍按 2772×1280，部分直接裁图的任务也不走统一映射。

**建议**：明确截图坐标、归一化坐标、真实触摸坐标之间的转换，全部识别和点击统一经过映射。若暂时不能保证，降级时明确停止任务，避免假装兼容后误点。

**验收**：强制触发缩放失败，检查 ROI、模板、返回匹配点和点击位置能否一致；无法支持时应清晰失败。当前固定设备的正常路径成功不能证明这个分支有效。

## R12：默认项目入口与实际部署入口不一致

**位置**：[project.json](../project.json)，6 行；[main.js](../main.js)，56–60 行；[tools/log_server.py](../tools/log_server.py)，39–48 行。

项目默认入口指向旧的 `main.js`，它未加载邮件、小乔模块，日志接口也缺少新模块使用的 `w()`；而文档当前使用的是生成后部署的 `_main.js`。电脑服务只有在 bundle 存在时才替换返回它。

直接按项目入口运行或缺少构建产物时，可能走到另一套行为，出现任务不存在、警告日志方法缺失以及截图初始化策略不一致等问题。

**建议**：统一受支持的启动方式，旧入口应明确转交到正确实现或停止使用；文档、项目配置、构建产物和远程服务保持一致。

**验收**：分别验证项目入口启动、按文档部署启动、远程启动和构建产物缺失；不允许无提示地退回不同实现。

## 后续 Agent 的交付要求建议

1. 开始修复前检查当前工作区与分支，确认本文基线之后是否已有相关变更，避免覆盖其他修改。

5. 把实际执行过的验证与尚未验证的假设分开记录。未经真机验证不要把静态推断写成已实测通过。
