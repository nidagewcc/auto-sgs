1. 快捷圆盘任务按钮的闭包绑定；

## 2. 高优先级问题

### 2.1 快捷圆盘任务按钮共享循环变量，点击时可能访问 `null.id`

**位置**

- `src/ui.js:237-270`

**代码路径**

`_dockRow()` 在 `for` 循环中通过 `var t = items[i]` 保存任务，并让多个 `OnClickListener` 的回调闭包引用这个 `t`。

按照 JavaScript 的 `var` 函数作用域和闭包语义，这些回调共享同一个变量。循环结束后，`t` 是最后一项；当前每行第三项为 `null`，因此任务按钮点击时可能在以下位置出错：

```javascript
self.runTask(t.id, t.title);
```

**影响**

- 快捷圆盘中的“人 / 邮 / 乔 / 日常 / 截图”按钮可能无法启动对应任务。
- “更多”按钮不引用 `t`，所以可能表现正常。
- 完整面板走 `_row(t)`，参数由每次函数调用独立绑定，不受同一问题影响，因此可能出现“完整面板能用、快捷圆盘不能用”的差异。

**修复建议**

- 保持 Rhino/ES5 兼容，优先抽成 `_dockCell(t)` 等函数，让 `t` 成为每次调用的独立参数；也可用立即执行函数显式捕获。
- 不建议在未确认 AutoJs6 Rhino 兼容级别前直接依赖 `let` 解决。

**建议验收**

逐个点击快捷圆盘的五个任务入口，确认每次都只启动所点任务，且日志中的任务 id 正确；再确认“更多”仍能打开完整面板。

### 2.2 防并发只维持 300 秒，短于小乔任务允许的执行时间

**位置**

- `src/ui.js:470-512`
- `src/ui.js:515-563`
- `src/tasks/xiaoqiao.js:34-35`

**代码路径**

```javascript
isBusy: function () {
    if (!this._t0) return false;
    return (new Date().getTime() - this._t0) < 300000;
}
```

小乔任务的 `RUN_TIMEOUT` 为 420000ms，且任务开始前还可能执行最长 120000ms 的 `game.ensure()`。因此旧任务仍运行时，`isBusy()` 就可能重新返回 `false`。

**一个具体的竞态过程**

1. 小乔运行超过 5 分钟但尚未结束；
2. 用户启动邮件，新任务覆盖 `sgs.ui._thread`；
3. 小乔与邮件同时截图、识图和点击；
4. 小乔先进入 `finally`，将共享的 `_t0`、`_thread` 清零；
5. 邮件仍在运行，但系统已显示空闲，第三个任务又可启动。

**影响**

- 多任务同时操作同一游戏画面。
- 点击落在错误页面，导致任务失败或误操作。
- 小乔可能被重复开启，涉及元宝消耗。
- “停止当前任务”只能引用最后被保存的线程，旧线程可能失去句柄。

**修复建议**

- 忙碌状态应由任务是否真正退出决定，不应由固定时长自动过期。
- 如果需要看门狗，应单独记录 `lastProgressAt`，超时后进入明确的取消/卡死处理流程，而不是直接宣告空闲。
- `finally` 清理状态前，应确认当前任务仍是登记的活动任务，避免旧任务清掉新任务状态。

**建议验收**

使用不点击游戏的模拟长任务进行测试：运行超过 5 分钟后，再次启动任务必须被明确拒绝或排队；旧任务结束时不得清除新任务的运行状态。

### 2.3 HTTP `run:` 指令会主动清空忙碌状态，可立即绕过防并发

**位置**

- `tools/build.py:259-262`
- 生成后的对应逻辑位于 `build/bundle.js`，但应修改源模板后重建。

**代码路径**

```javascript
var tid = cmd.substring(4);
sgs.ui._t0 = 0;
sgs.ui.runTask(tid, "远程-" + tid);
```

**影响**

任意 `run:` 指令都会先清除现有忙碌标记，再创建新任务。重复投递 `run:xiaoqiao` 等指令时，不必等待 5 分钟即可形成并发。

**修复建议**

- 删除强制清零。
- 远程指令和 UI 点击必须走同一个任务调度入口。
- 忙碌时应返回明确的“拒绝”或“已排队”结果，不能静默覆盖状态。

### 2.4 `stopAll()` 不等待旧任务退出，旧任务的 `finally` 可能干扰新任务

**位置**

- `src/ui.js:500-511`
- `src/ui.js:551-562`
- `src/ui.js:566-573`

**代码路径**

`stopAll()` 调用 `interrupt()` 后立即执行：

```javascript
this._t0 = 0;
this._thread = null;
```

但图像识别、OCR、HTTP 等调用是否立即响应中断，不能仅由这里保证。旧任务可能尚未完成退出，而新任务已被允许启动。旧任务之后的 `finally` 又会无条件清理共享状态。

**影响**

- 手动停止后可能仍有点击发生。
- 新旧任务并发。
- 新任务的线程句柄和忙碌标记被旧任务清掉。
- 一键日常内部的单步 `catch` 还需要特别检查：中断异常被单步捕获后，是否仍会继续下一步。

**修复建议**

- 引入明确的任务状态，例如 `idle / running / cancelling`。
- 设置取消标志并 interrupt，等任务线程完成收尾后再回到 `idle`。
- 在任务循环和每个阶段边界检查取消标志。
- `runDaily()` 收到取消后不得继续执行后续步骤。

### 2.5 小乔识别失败后仍盲点固定坐标，可能在不正确页面执行耗元宝操作

**位置**

- `src/tasks/xiaoqiao.js:65-75`
- `src/tasks/xiaoqiao.js:78-89`
- `src/tasks/xiaoqiao.js:146-154`

**代码路径**

当前策略依次为：

1. 找不到头像，就假定“助手面板已打开”；
2. 三轮找不到“开启”模板，就返回固定坐标 `(1900, 940)`；
3. `run()` 最终无论真实匹配点是什么，都点击固定 `KAIQI_POINT`。

**触发场景**

- 头像模板因 UI 更新、暗色遮罩或分辨率变化而未命中；
- 面板实际未打开；
- 页面不是日常功能页；
- 识图插件临时异常，导致所有匹配均返回空。

**影响**

脚本会把“识别失败”当成“可以继续点击”，在最需要停止的时候继续操作。该步骤可能消耗元宝，风险高于普通导航误点。

**修复建议**

这里应采用 **fail-closed**：

- 未确认面板和“开启”按钮时直接报错；
- 头像未找到时重新确认当前页面，而不是推断面板已开；
- 真实模板命中后再点击匹配中心；
- 固定坐标兜底若确需保留，应放到显式调试开关下，默认关闭。

**建议验收**

在测试环境模拟 `_findAvatar()` 和 `waitImage()` 均返回空，任务应在任何固定坐标点击前失败，并保留截图和明确错误日志。

### 2.6 文件投递的 `__busy` 只覆盖“启动任务的包装线程”，不覆盖实际任务

**位置**

- `tools/build.py:237-246`
- `src/ui.js:475-512`

**代码路径**

心跳线程先创建包装线程，包装线程再调用 `sgs.ui.runTask()`；而 `runTask()` 内部又创建一个任务线程并立即返回。因此：

```javascript
__busy = true;
// 包装线程中：
sgs.ui.runTask(tidc, "投递-" + tidc);
__busy = false;
```

`__busy=false` 实际表示“包装线程返回”，并不表示游戏任务完成。

**影响**

- 下一条文件指令可能在实际任务运行时被读取并删除。
- `runTask()` 若因忙碌直接返回，调用方收不到失败结果，该指令就被静默丢弃，而不是排队。
- 超过 300 秒后，又可能演变成实际并发。
- 启动时的“冒烟任务结束”日志也会在任务刚启动时提前打印，见 `tools/build.py:154-164`。

**修复建议**

- 最稳妥的方案是一个长期存在的单 worker，从队列逐条取任务并同步等待任务完成。
- 不建议继续叠加 `__busy`、`_t0`、`_thread` 多层布尔/时间状态。
- 若选择拒绝而非排队，也必须在读取文件前决定能否接收，或把拒绝结果可靠记录并保留可重试信息。

**建议验收**

运行一个模拟长任务期间连续投递两条指令：第二条应按设计排队或明确拒绝，不能无提示消失；日志中的开始/结束时间必须对应真实执行区间。

## 3. 中优先级问题

### 3.1 小乔左上角返回兜底重复判断同一张缓存截图

**位置**

- `src/vision.js:79-82`
- `src/tasks/xiaoqiao.js:135-143`

**代码路径**

`isHome()` 未传图片时使用 `this.frame()`，而 `frame()` 默认优先返回 `_img` 缓存。以下循环点击返回后，没有任何 `frame(true)`：

```javascript
for (var q = 1; q <= 3 && !sgs.vision.isHome(); q++) {
    v.clickPointAt(70, 70);
    sleep(2500);
}
if (!sgs.vision.isHome()) throw new Error(...);
```

**影响**

- 第一次点击已回主城，后续仍可能基于旧图继续点返回。
- 最终确认也可能使用进入分支前的旧图，错误抛出“未能回到主城”。
- 该分支本意是陌生页面自愈，但缓存使观察与操作脱节。

**修复建议**

每次点击并等待后显式调用：

```javascript
sgs.vision.isHome(v.frame(true))
```

最终确认同样必须取新帧。可进一步搜索所有“点击后调用无参数 `isHome()`”的路径，统一检查。

### 3.2 邮件未识别到“全部领取”仍可能报任务完成

**位置**

- `src/tasks/mail.js:37-49`
- `src/tasks/mail.js:51-74`

**代码路径**

领取阶段未命中按钮时只记录日志并 `break`。之后只要能关窗并回到主城，任务就正常返回，UI 显示完成。

**为什么值得单独处理**

项目文档说明“没有可领邮件时按钮也不会消失”。因此在邮件弹窗已经确认打开的前提下，始终找不到按钮更像是模板、截图或页面状态异常，不应直接等价于“无可领邮件”。

**影响**

- 模板失效或 loading 吞点击时，邮件未领取但显示完成。
- 一键日常会把该步骤计入 `done`。
- 用户只能翻日志才能发现“未检测到全部领取按钮”。

**修复建议**

- 弹窗打开后，领取按钮经过完整重试仍未识别，应让任务失败或返回 `skipped_with_reason`，不要返回成功。
- 若以后能识别“空邮箱”独立标志，可单独处理空邮箱情况。
- 任务最好返回结构化结果，例如 `claimed / empty / failed / unknown`，而不是只有异常和成功两种状态。

### 3.3 截图未上传时仍提示“截图已上传”

**位置**

- `src/ui.js:481-490`
- `tools/build.py:72-83` 中的 `sgs.pushShot()`

**代码路径**

`pushShot()` 在未配置 `sgs.PC`、失败次数达到阈值或上传异常时直接返回/吞掉异常；调用方不检查结果，固定记录“截屏已回传”并 toast“截图已上传”。

**影响**

- 脱机模式点击截图，也会提示上传成功。
- 服务不可达或 HTTP 错误时，用户得到错误反馈。

**修复建议**

让 `pushShot()` 返回明确状态，至少区分 `uploaded / disabled / failed`；UI 根据结果显示“已上传 / 未配置回传 / 上传失败”。同时检查 HTTP 状态码，不能只依赖是否抛异常。

### 3.4 `main.js` 与 bundle 启动逻辑漂移，直接项目入口运行会缺少任务

**位置**

- `project.json:6`
- `main.js:7-10`
- `main.js:39-49`
- `main.js:56-60`
- `tools/build.js:10-18`

**差异**

`project.json` 的入口是 `main.js`，但该文件：

1. 只加载 `playerinfo.js` 和 `ui.js`，未加载 `mail.js`、`xiaoqiao.js`；
2. `sgs.log` 只有 `i/e`，而公共层和任务会调用 `sgs.log.w()`；
3. 使用硬编码 `PC_BASE`，未采用新版 `sgs.PC` 脱机开关；
4. `pushShot()` 使用 `frame()` 缓存，bundle 中则使用 `frame(true)`。

**影响**

直接按 AutoJs6 项目配置运行 `main.js` 时，邮件、小乔和一键日常会报“任务不存在”；部分告警路径还可能因 `sgs.log.w` 不存在再次抛异常。

**边界说明**

文档中的 `bootstrap.js → log_server.py → build/bundle.js` 路径会拿到 bundle，因此不一定触发该问题。这是“直接入口”和“实际部署入口”不一致的问题，不应误判成所有现有真机流程都必然失败。

**修复建议**

- 让直接入口和 bundle 共用同一份启动模块；或
- 明确废弃直接运行方式，并调整 `project.json`、文档和构建产物，避免维护两份已经不同的启动器。

## 4. 长期运行与可维护性风险

### 4.1 大量 Image 对象未显式释放，需要真机确认 native 内存趋势

**位置示例**

- `src/vision.js:80-89`：新帧覆盖旧 `_img`
- `src/vision.js:101-160`：raw、clip、resize 多份图像
- `src/vision.js:219-228`：OCR 临时裁图
- `src/vision.js:247-257`：每次找图重新读取模板
- `src/vision.js:265-335`：模板和 ROI 裁图匹配

全项目 JavaScript 中未搜到 `.recycle()`。

**结论边界**

这足以确认“存在大量临时图像且没有显式释放策略”，但**是否已经造成不可回收泄漏或 OOM，需要真机内存数据验证**，不能只凭静态代码断言。

**修复建议**

- 制定清晰的图像所有权规则：谁创建、谁释放；共享帧由调用方统一释放。
- 对临时模板、OCR clip、归一化中间图，在 `finally` 中释放。
- 模板可按名称缓存，避免每次匹配重复 `images.read()`。
- 替换旧帧前释放旧帧，但要先排除仍被 `playerinfo` 多帧采样等逻辑引用的对象。
- 不要把仍在使用的共享图提前 recycle，否则会重新引入“图像资源已被回收”。

**建议验收**

连续运行识图/OCR 轮询数十分钟，定期记录 AutoJs6 进程内存和系统日志，比较修复前后的内存曲线及 GC 后基线。

### 4.2 `/cmd` 的失败计数从未递增，离线退避条件不会触发

**位置**

- `tools/build.py:170`
- `tools/build.py:252-255`
- `tools/build.py:334`

**代码路径**

代码检查 `__cmdFail >= 10`，成功时会清零，但末尾异常处理为空，没有 `__cmdFail++`。

**影响**

配置 `pc.txt` 后，如果电脑服务长期不可达，心跳仍会持续发起最长 8 秒超时的请求。名义上的 3 秒心跳会被拉长，本地文件指令检查和日志推送也可能被延迟。

**修复建议**

- 异常时递增失败计数，成功后清零。
- 增加有上限的指数退避和恢复探测。
- 将本地文件指令处理与网络轮询解耦，避免电脑离线影响本地控制。

---

### 4.3 日志和截图没有轮转或容量上限

**位置**

- `tools/build.py:36-44`：`LOGS` 数组与 `run.log`
- `tools/log_server.py:98-120`：电脑端日志、截图文件

**影响**

长期挂机时：

- 进程内 `LOGS` 持续增长；
- 手机 `run.log` 持续追加；
- 电脑 `_logs` 下截图和日志持续增加。

增长速度取决于任务频率和回传配置，属于慢性问题，但与常驻挂机目标直接相关。

**修复建议**

- 内存日志只保留最近 N 条或使用环形缓冲区。
- `run.log` 按大小/日期轮转，保留有限代数。
- 电脑端截图按时间或总量清理，并避免同秒文件名互相覆盖。

### 4.4 等级 OCR 的“更长后缀优先”不能解决所有已知误识别

**位置**

- `src/tasks/playerinfo.js:67-106`
- `src/tasks/playerinfo.js:114-124`

**代码路径**

投票平票时优先位数多的值，并在某候选是另一候选后缀时选更长者。这可处理部分 `120 → 20`，但无法处理注释中同样提到的 `120 → 920`；解析器本身也接受任意正的 1～3 位数字。

**影响**

异常 OCR 结果可能被当成合法等级输出，且当前策略给人一种“已经通过投票纠正”的错误安全感。

**修复建议**

- 增加合理等级范围校验；范围应配置化，避免游戏开放新等级后失效。
- 无可靠多数或候选冲突时返回“无法确定”，不要强行猜值。
- 为 `_pick()` 和 `_parse()` 添加纯 JavaScript 单元测试，覆盖 `120/20/920/12093/空文本` 等样本。

### 4.5 开发服务监听全部网卡且 `/cmd` 无认证

**位置**

- `tools/log_server.py:87-94`
- `tools/log_server.py:126-128`

**代码路径**

服务绑定 `0.0.0.0:8099`，`/cmd` POST 不要求身份认证，指令包括运行任务、停止、清理引擎和 reload 等。

**影响**

在不可信局域网中，其他设备可能投递指令、干扰任务，甚至触发小乔等涉及资源消耗的流程。

**修复建议**

- 给指令端点加入足够长的随机 token，token 不要提交进仓库。
- 用 Windows 防火墙限制仅允许手机 IP 访问该端口。
- 不需要远程指令时关闭该端点或服务。
- 如需进一步提高文件服务边界，可将 `target.startswith(BASE)` 改为 `os.path.commonpath()` 等可靠的路径归属检查。

## 5. 建议的整体改造方向

### 5.1 把任务执行统一成一个调度器

当前问题并非单点，而是 `_t0`、`_thread`、`__busy`、HTTP 强制清零和包装线程共同造成。建议统一为：

```text
UI 点击 ───────┐
文件指令 ──────┼─> 同一个任务队列/调度器 ─> 唯一 worker ─> 任务函数
HTTP 指令 ─────┘
```

调度器至少负责：

- 唯一活动任务；
- 排队或明确拒绝；
- `idle/running/cancelling` 状态；
- 取消传播；
- 真实开始/结束日志；
- 旧任务不能清理新任务状态；
- 执行结果结构化返回。

### 5.2 涉及资源消耗的步骤默认 fail-closed

小乔“开启”等操作应遵循：

```text
确认当前页面 → 确认目标按钮 → 点击 → 验证页面变化/执行信号
```

识别失败时保存截图并停止，不要用固定坐标继续试探。普通返回、关闭等低风险导航可以保留有限兜底，但两种操作应区别处理。

### 5.3 区分“执行动作”和“业务成功”

- 点击过“全部领取”不等于确认领取完成；
- 调用过 `pushShot()` 不等于上传成功；
- 创建过任务线程不等于任务结束；
- 回到主城不等于前一个业务动作已成功。

建议任务返回结构化结果，UI 和一键日常依据结果记录 `done / failed / skipped / unknown`。
