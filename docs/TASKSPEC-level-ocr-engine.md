# 等级 OCR 引擎层加固方案草案（2026-11-27）

状态：**调研与实现前置条件待补齐，不可直接按本草案修改生产代码**。职责：探针补充样本与真机能力验证，Chief 确定参数与验收后派码工实现；本文不涉及真机操作。

## 1. 问题与证据边界

- `docs/PROBE-LEVEL-ROI-2026-11-27.md` 记录旧 ROI 下文本完整但边距很小、跨账号横向漂移 74px；新 ROI 为 `[1045,488,1305,600]`，坐标基于归一化 2772×1280 画布。
- `docs/VERIFY-LEVEL-MAIL-2026-11-27.md` 记录账号「产品经理」真实 120 级，新 ROI 三帧原文为 `["120级","20级","20级"]`，最终值 120 来自现有后缀补救。探针报告另记录「黄天当道」为 120 级。两次样本不是同账号；不能从不同采集时刻和账号的结果推断命中率或确定单一引擎根因。
- 新 ROI 未满足三帧原文全部完整的目标。OCR 检测、识别、画面内容及预处理均可能影响结果，目前证据不足以确定哪种手段能修复。

## 2. 现有链路

`src/tasks/playerinfo.js` 先调用 `frame(true)` 最多采集三帧、间隔 220ms，仅成功帧进入 `imgs`；等级逐帧调用 `vision.ocrRect(rect, imgs[t])`，原文进入 `samples` 和日志，再由 `_parse("level", raw)` 提取首段数字、`_pick` 投票及后缀补救。实际抓到少于三帧时现在仍会继续，验收必须检查帧数。

`src/vision.js` 的 `ocrRect` 先按 `_mapRect` 处理可能存在的缩放映射，再用 `images.clip` 裁图、交给 `_ocr`；`_ocr` 优先尝试 `gmlkit.ocr(img, "zh")`，否则尝试 `ocr(img)` 并将数组连接成字符串。现有代码未证明 OCR 支持字符白名单，也未证明任何二值化 API 的具体签名与可用性。`frame` 的缓存及延迟回收服务多个字段，改动不能回收调用方持有的原帧。

现有 `samples` 是 OCR 原文的数组；验收须保留各帧实际 OCR 输出，不能用拼接、补位或投票结果伪造为原文。现有 `_pick` 假设漏前导位而倾向较长后缀候选，这不是可信度保证，本任务不得把它当作三帧原文达标的证据。

## 3. 候选方案比较

| 方案 | 原理与改动面 | 风险及对其他字段的影响 |
|---|---|---|
| 等级 ROI 内二值化预处理 | 保持原始截图与现有 ROI，对每个等级裁图单独转换对比度/阈值，再交现有 OCR；需确认图像 API、极性、阈值、缩放映射和资源回收。 | 细字可能被抹掉或背景变成噪声；不同皮肤和光照不一定通用，额外计算与临时图会占内存。仅对 level 的副本处理可隔离其余字段；不得全局更改 `_ocr` 或原帧。 |
| 数字白名单或正则纠偏 | 若具体 OCR 引擎确实支持，可限制识别字符；正则只约束已有文本的格式、剔除杂字符。需先实测接口和返回格式。 | 白名单可能去掉「级」并影响原文验收；正则和白名单**不能凭空恢复已漏掉的首位**，直接给 `20` 加 `1` 会误报真实 20 级。仅限等级字段才能避免影响昵称、单位及分数。 |
| 首位单字补扫 | 另取等级相关局部区域进行 OCR，结合完整候选的空间位置和置信证据辨认首位；需要可靠定位与组合规则。 | 现有封装只返回文本，无字符框和置信度；账号间漂移使固定首位坐标不可靠，背景可能误读为数字。拼接推断值不是单次 OCR 原文，不能冒充原文或满足三帧原文要求。局部限定 level 可隔离其他字段。 |

## 4. 推荐路线及实现前置条件

优先由探针验证**等级 ROI 副本的二值化预处理**，因为它直接改善 OCR 输入，理论上可保留每帧独立 OCR 原文，并可隔离其他字段；当前没有可执行的阈值或 API 实测，推荐仅是待验证假设。若预处理不能稳定改善，不以白名单、正则、固定补 `1` 或未经定位的单字拼接冒充解决；由探针提交新证据后重新设计。

实施前探针须提供文字补充并交 Chief 确认：

1. 在授权设备的实际 AutoJs6 版本和当前 OCR 引擎上核实图像预处理 API 可用性、精确调用签名、输入输出类型、是否返回新图及回收约束；不能只凭 API 名称推测。记录引擎实际分支、版本与异常行为。
2. 对两个真实等级经用户或主城画面核实为 120 的账号，提供同屏原始 ROI 样本与对应 OCR 原文；覆盖正常、漏首位及尽可能的不同背景。记录账号、采样时间、帧数、画布尺寸及坐标，确保对照来源可复核。两个账号若不再是 120 级，应记录其真实值并另定验收，不能把 120 当成通用等级。
3. 在同一批帧上比较原图与候选预处理的逐帧原文，提供具体算法、颜色极性、阈值或其他参数、裁剪顺序、缩放和裁图边界策略、失败回退策略，以及负样本（尤其真实低等级、其他首位及背景干扰）的误识别结果。明确三帧原文采用哪一路 OCR 输出及异常时的保守行为；不得根据已知账号等级选择或补造结果。
4. 验证 `_scale` 映射模式与正常归一化模式、图像尺寸边界和临时图所有权；给出失败、空结果、取消时资源释放与日志要求。确保原始帧及其他字段不受影响。补充可接受的时延和内存预算及测量方法，再由 Chief 确认具体界限。

前置数据不足时仅保留草案，不猜测二值阈值、补扫坐标、白名单能力或上线成功标准。

## 5. 待确认的实现约束与本地测试

- 处理仅作用于等级字段，不改变其他字段 OCR、现有采帧数量、投票、解析或全局引擎；除非后续文字 spec 明确授权。所有临时图在成功和异常路径按已验证 API 所有权释放，不回收原始采样帧。
- 保持 `samples` 可追溯到各帧真实 OCR 输出；如要比较预处理前后原文，须分别标明来源和帧号，不能将推断值当原文。异常、空字符串和实际采帧不足应可见，不能伪报三帧成功。
- 本地纯逻辑测试用 mock 图像和 OCR，不依赖手机或收费依赖：验证仅 level 调用预处理、每帧输入和输出对应、其他六字段走旧路径；覆盖预处理异常、空 OCR、图像对象别名及释放、坐标映射、不足三帧；断言不硬编码 120 或擅自补前导位。对真实 20、120 和不同首位的模拟输入验证不凭空补位，既有 `_parse`/`_pick` 行为保持不变。
- mock 测试只能验证调用与逻辑，不能证明真实图像处理 API 可用、OCR 精度、耗时或内存；这些必须由探针真机测量。
- 实施后的本地交付依次运行 `node tools/build.js`、`node --check build/bundle.js`、`node tests/regression.js` 和相关专项测试，并检查 `git diff --check`；未实际改代码前无需运行这些构建。
